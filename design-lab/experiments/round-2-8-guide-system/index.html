Reading Family

One guide, two modes, one shared chapter contract.

The point of this round is not just visual polish. It is to prove a cleaner architecture for Guide 101 and Guide 201/301: the same chapter flow should support an interactive web guide and a coherent PDF/static guide without duplicating the whole product twice.

Shared reading spine

Cover, orientation, chapter rhythm, instructional prose, and next-step framing stay stable across both modes.

Interactive enhancement

Web mode gets calculators, chips, explainers, and scenario moments after the lesson lands.

Static PDF fallback

PDF mode keeps the same chapter logic but swaps tool blocks for static figures, worked examples, and concise interpretation.

What 2.8 is trying to settle

The earlier rounds proved that the guides belong in the Reading family. This round goes one level deeper and asks how the guide system should actually be built.

1. Shared chapter data

Each chapter should define its lesson, examples, and fallback story once. Interactive and PDF modes should be render decisions, not separate products.

2. Shared shell

The same cover, chapter rail, section framing, and CTA/endcap model should work in both outputs, with only the navigation behavior changing.

3. Mode-specific blocks

Interactive moments should always declare what their PDF/static replacement is. That rule needs to exist at design time, not only at export time.

Architecture view

Layer 1 - chapter content Headline, promise, explanation, worked example, takeaway, next step.
Layer 2 - guide shell Cover, rail, TOC, chapter opener, section framing, CTA, footer.
Layer 3 - mode blocks Interactive mode gets calculators and exploration cards. PDF mode gets static figures, example outputs, and concise interpretation.
Layer 4 - output render Web guide: sticky rail, active section highlight, richer interaction. PDF guide: same reading flow, no dead controls, no missing meaning.
